## 0. 背景与现状

- **产品定位**：RedBeacon = 小红书 AI 运营「数字员工」CLI（生成 / 审核 / 发布 / 多账号矩阵）。它是作者的第一个数字员工作品，**远期愿景是做"数字员工市场"**，本方案的后端架构要为这个愿景打地基。
- **现有形态**：
  - 闭源 Python CLI（`redbeacon`，setuptools 打包），由 AI agent（Claude Code skill / Codex）通过命令编排。
  - skill 层 = 一组 markdown 命令（开源，用户可见可改）。
  - 飞书多维表格 = 内容审核表（生成后推送、人工审核改稿标通过、发布读取）。
  - aihub（`https://aihub.jidouqie.com/v1`）= AI 中转代理，按 per-user key 调用。
  - 授权 = Ed25519 签名「解锁码」，绑机器码、离线校验。
- **交付模式**：寄生宿主 + 人工上门交付，客户是非技术博主。

### 本次重构要解决的四件事
1. **数据架构**：业务数据散在本地 SQLite，与飞书双写产生「孤儿/待审数虚报」类 bug → 改为**单一真源**。
2. **选题能力太薄**：选题只是一句话标题，撑不起深度运营，也撑不起新增的「仿写」功能。
3. **授权/计费尴尬**：解锁码买断 × 持续烧成本，结构错配、防不住、撑不起额度计费。
4. **新增「仿写/抄爆款」功能**。

## 1. 数据归属总原则（本地 vs 飞书）

✅ **判断标准**：高频被人改的、列表型的、需异步/移动端 touch 的、属于"人拍板"环节的业务数据 → 飞书；敏感凭证/身份/读多写少的单条富文档 → 本地或服务端。

```
🔒 本地内核（只装隐私 / 钥匙 / 身份，绝不上传平台/第三方）
   · AI 网关会话 token
   · 小红书登录态 cookie、浏览器 profile（cloakbrowser）
   · 机器码（设备指纹）
   · 代理凭证
   · 用户自己的飞书应用凭证（app_id / app_secret）——见 §2.3：每用户自带飞书应用，
     此密钥只能访问该用户自己的飞书，扒出来也只碰自己数据，零跨用户风险，故可安全放本地

☁️ 飞书 = 唯一业务数据中心（每用户自己租户内，一号一多维表格）
   · 账号数据 / 策略
   · 选题表（选题 + 灵感合一，活跃）
   · 文案审核表（未审 / 通过 / 发布失败）
   · 归档表（已发布 = 数据资产）
   · 数据分析表（后期付费版，预留）

🚫 不设本地缓存（已定）：CLI 每次直连飞书；"图片下载到本地"是发布素材、非缓存。
   强依赖网络是网络应用的设计初衷（大模型本就要联网、飞书顺带），换得换设备续进度、不挑地点。
```

⚠️ **铁律**：追求的是「业务数据单一真源」，飞书只是承载它的面。单一真源直接消灭现存的「孤儿/待审数虚报」那类双写漂移 bug。

## 2. 飞书结构

### 2.1 层级（务必分清三个概念）
```
自建应用(app，一把钥匙，有 app_id/app_secret)
  └─ 可访问 多个「多维表格」(Base，容器，有 app_token)
       └─ 每个多维表格内含 多张「数据表」(Table，底部 tab，按表名区分)
            └─ 每张数据表 再开 多个「视图」(View)
```

### 2.2 账号维度：✅ 一个小红书号 = 一个多维表格(Base)
```
用户自己的飞书自建应用(自己的租户)
 ├─ 多维表格·账号A ─ 数据表[账号数据][选题表][文案审核表][归档表][数据分析表(预留)]
 ├─ 多维表格·账号B ─ 同上
 └─ ...
```
- **表类型用「数据表」分，账号用「多维表格」分。**
- 一号一 Base 的理由：①账号天然隔离，将来能把某号的 Base 单独授权给对应客户；②躲开飞书多维表格的单表行数上限；③视图/分组不被别的号干扰。
- ✅ **后期加表（如数据分析）= 往现有 Base 加一张数据表，不新建多维表格、不动绑定。**
- ✅ config 里每号**绑一个多维表格的 app_token**（= 多维表格链接里 `base/` 后那串，如 `https://xxx.feishu.cn/base/{app_token}`，`?table=…&view=…` 等参数都不要），下面各数据表用**约定表名**定位（比现在绑一堆零散表清爽）。

### 2.3 应用归属：✅ 每个用户绑自己的飞书企业自建应用（自己的租户）
- **不是平台方一个应用管所有人**；每个用户在自己的飞书租户里建自己的自建应用，绑自己的 app_id/app_secret。
- 安全收益（关键）：用户的飞书钥匙**只能开自己家的门**——扒出来也只碰自己数据，**天然无跨用户风险**；账号间是不同租户、物理隔离。
- 代价转移到"开通"：非技术用户要自己在飞书开发者后台建应用、配多维表格权限。用**引导视频 + 使用简介**解决（目标用户≈会配 Codex/Claude Code 的人，门槛可接受）；后续可考虑 API 辅助开通，先让用户自己动手。
- 多账号矩阵：同一用户名下多个小红书号，可共用该用户自己的一个飞书应用（同租户多 Base），由用户自定。

### 2.4 开通：✅ 已验证可全自动（沿用现有机制，扩成满配模板）
- **机制（现有代码已跑通、无需用户手动）**：作者维护一个**公开权限**的模板 Base（写死 app_token，现为 `_FEISHU_TEMPLATE_APP_TOKEN`）→ 用**用户自己的自建应用**凭证调 `POST /drive/v1/files/{token}/copy`（失败回退 `POST /bitable/v1/apps/{token}/copy`）把模板**整体复制进用户自己的租户**（副本归用户租户）→ 再 `POST /drive/v1/permissions/{app_token}/members` 加协作者 + `.../transfer_owner` 转所有者。全程纯 API。
- **为何不撞跨租户禁制(1064510)**：源是公开可读、复制目标落在调用方（用户）自己的租户 → 是"在自己租户内创建副本"，非跨租户搬运。参考实现：`cli/src/redbeacon/services/feishu.py`、`feishu_api.py`。
- **本次只需做的事**：把模板从"单张审核表"**扩成满配 4 表 Base（含字段/视图）**。`/copy` 复制 bitable 文件会**整表带走所有数据表/视图**，一次 copy 就把整套结构搬过去，**不用逐张建、不用手动**。
- **保留的稳健性**：① 复制后 API 校验结构、按名补齐缺项（幂等，半成品可重跑）；② 实测自动化/表单/跨表双向关联是否随 copy 保真（不保真就改为复制后用 API 补建）；③ copy/授权失败降级（现有代码已回退为共享原模板）。
- 远期：源 Base >5 万条记录时 /copy 只复制结构——空模板无影响。

### 3.1 设计哲学
- ✅ **选题从"一句话标题"升级成"创作简报 brief"**：核心必填、蓝图可空、来源选填；能继承账号定位的默认继承，只在偏离时才填。
- ✅ **出生轻、随生命周期变厚**：规划会量产一句话选题（蓝图全空）；坐下写时补蓝图；仿写入口天生满配。
- ✅ **灵感 = 早期选题**，同一条命的不同成熟度，用「阶段」字段流转，靠视图切分"灵感库 / 选题库"两个面板，不拆两张表。

### 3.2 字段（分四层；多数可空，靠视图隐藏，不做成 20 格表单）

> 现有的自由字符串 `note`/`--idea` 拆进「切入角度」+「要点提纲」。`generate` 从"吃标题+idea"升级成"吃整份 brief"，空字段自动从【账号设定】补默认 —— **飞书只存"偏离值"，不重复存定位**。

### 3.3 视图（飞书杀手锏，解决"字段多但不挤"）
1. **💡灵感箱**：筛 `阶段=灵感`，只显示 选题/来源类型/对标链接。用户在这儿审阅 AI 录进来的灵感、改、拍板。
2. **📋选题盘面**（按应用域分组）：筛 `阶段=选题`，看覆盖匀不匀。规划会看这个。
3. **✍️写作台**：筛 `阶段=选题 且 优先级=高`（或本周要写），显示全部蓝图字段，人和 AI 在这儿把 brief 填满。
4. **🗂️看板**（按阶段分列拖动）：灵感→选题→已生成→已发布，内容日历的掌控感来自这里。

### 3.4 全生命周期（跨 4 张表流转，热/冷分离）
```
[选题表]                         [文案审核表]                  [归档表]
💡灵感 ─人拍板→ 📌选题 ──写成文案──▶ 📝未审 ⇄ ✅通过 ─发布成功─▶ 🗄️已发布(数据资产)
                 (选题表删除,            ↘ ❌发布失败(留此重试)
                  brief 快照进文案)
```
- **灵感→选题**（选题表内）：只能**人**推（战略层拍板铁律）。灵感与选题同住「选题表」，写文案前都在这张活跃表。
- **选题→文案**：`generate` 写成文案后，**该选题从选题表删除**，其 brief（角度/提纲/对标来源）**快照进新建的文案记录**，进入「文案审核表」。选题历史不丢——它活在文案里（文案=选题的成品形态）。
- **文案审核表**只保留三态：未审核 / 通过 / 发布失败。CLI 发布只读「通过」。
- **发布成功 → 移入「归档表」**（= 数据资产、复盘锚点）。移动 = 归档表新建 + 审核表删除（飞书无原生 move）；半路失败风险**已接受**，靠对账兜底扫孤儿。
- 防膨胀：活跃两表（选题/文案审核）始终小 → CLI/AI 上下文不浪费；历史沉到归档表。
- ⚠️ §6.5：飞书可被用户手改成非法状态，CLI 读取须按不可信数据做防御性校验。

### 3.5 ⚠️ 录入/编辑分工（重要交互原则）
- **录入是 AI 的活**：不管来源是 skill 对话窗口发的爆款链接/文案、规划会生成的、还是仿写提取的，**全部由 AI 写进飞书表**。
- **用户在飞书表里只做"改"**：调角度、改优先级、删、拍板转阶段、改稿标通过。
- 飞书表对用户 = **审阅/微调台**，不是录入表单（一致于"压低用户输入成本"理念）。
- 权衡：录入统一走对话窗 → 放弃了"飞书 App 随手丢链接"的便利（用户看到爆款得开 skill 窗口发）。✅ 取一致性。飞书不禁止手动加行，重度用户手敲一条算兜底、非主路径。

### 3.6 账号数据表（as-built，键值布局）
`tbljenmcBEU10eJd`。**单条记录**的账号档案，故用**键值布局**（列：`配置项 ｜ 分组 ｜ 值 ｜ 说明`），26 行/每行一个配置项，按分组：**标识 / 定位内核 / 策略 / 文案预设 / 视觉发布**。配置项 = CLI 现有定位字段（赛道/受众/痛点/差异化/变现/内容支柱/语气/开头风格/排版风格/emoji/篇幅/文案指南/违禁词/视觉风格/发布节奏）+ 专业补充（一句话定位、人设·我是谁、用户利益点·爽点、账号阶段与目标、对标账号、账号级关键词、话题标签策略、选题边界·不做、默认配图方式、账号备注名、小红书昵称）。键值布局的代价：丢单选类型约束、CLI 按"配置项找行"读。选题表的"继承默认"从这张取值。

> **账号提示词放哪、怎么不割裂（已定）**：账号"提示词"拆两半——① **骨架/模板**（怎么拼、固定话术）= 生成引擎逻辑，**留 CLI 代码**，不是账号数据；② **账号专属变量**（定位/受众/`文案指南(copy_guide)`/语气/视觉…）= 业务数据，**唯一真源 = 本账号数据表（飞书）**。
> 不割裂三条：(a) `generate` 改为**从飞书账号数据表读**这些变量拼提示词，不再读本地 SQLite 策略；(b) 本地网页面板**二选一**：退休（直接在飞书表改，飞书即"作战室"）或改造成"读写飞书的瘦壳"（只是更好看的编辑器、背后存飞书）；**严禁本地存一份+飞书存一份、两处都能改**；(c) 提示词骨架留代码（非账号数据、无割裂问题）。

> **定位 skill 要做"深度账号梳理"（已定）**：账号数据升级成 ~26 字段后，定位环节需带用户把整个账号思路理清（赛道/受众/痛点/人设/差异化/对标/边界/阶段…全覆盖）。但**深度在"覆盖"不在"拷问"**——不是抛一堆空问题，而是 **AI 联网+引导先替用户把每个字段起草一版，用户逐块确认/微调**（呼应"录入是 AI 的活、用户只改"，聊得深但用户主要拍板和修、不打字）。配套：核心层(赛道/受众/内容支柱)先钉死、蓝图类(人设/对标/边界)先草拟再磨；少数字段要用户给料(对标账号具体名、变现意图)；定位 skill 直接写飞书账号数据表(单一真源)，写完顺带铺第一批选题。

### 3.7 文案审核表（as-built，兼容旧版）

## 4. 新增功能：仿写 / 抄爆款

### 4.1 定位
内容引擎的**第三个输入源**（前两个：选题库抽题、单篇共创）。本质 = 对标驱动创作。

### 4.2 流程
```
用户在 skill 对话窗口发链接/文案
   → 提取（adapter 按平台路由）
   → 对标拆解（AI：扒可迁移的钩子/结构/选题角度，丢掉"关于他"的噪音）
   → 拟成满配 brief 落进飞书【选题灵感库】(阶段=灵感，对标来源层填满)
   → 人拍板转「选题」 + AI 补蓝图
   → 复用现有 generate 生产
```
🔶 默认走选题层（保战略层/查重/可复用）；给一个"信得过直出"的快捷。

### 4.3 ⚠️ 红线：仿结构、不抄字
- 提取的原文只作"结构参考"，**禁止整句复用**，必须换成本账号的场景/例子/口吻。
- RedBeacon 天然占便宜：**图是自己生成的**（绕过盗图检测），文字重新长，只借套路。

### 4.4 提取分档（⏳ v1 范围待最终拍板）
| 档 | 输入 | 如何拿文案 | 难度 |
|---|---|---|---|
| A | 直接粘贴文案 | 不用提取 | 极低 |
| B | 小红书图文笔记链接 | 复用 cloakbrowser 登录态会话抓页面 | 中 |
| C | 抖音/视频号/B站 视频链接 | 解析标题+简介+话题（梗概，非逐字口播） | 中，不全 |
| D | 视频逐字文案 | 下载视频→抽音轨→ASR 转写 | 重：下载+转写 API+成本+灰度风险 |

🔶 **建议 v1 先做 A+B**（最稳、最快、风险最低，复用现有浏览器）；C 次之；D（ASR）单独评估，别让 v1 卡在这里。

### 4.5 ✅ 计费归属（对接平台，见 §5.2）
- 仿写本身 = `features.mimic` 付费开关软解锁（订阅权益里带）；提取/拆解/改写跑宿主 AI（免费）。
- 仿写**重新出的配图 = 平台生图、扣算力点**（与普通生成走同一条 metered 路径）。
- 视频逐字（D 档 ASR）= 远期新增平台计量能力 `asr`（与生图同构），v1 不做。

## 5. 计费 + 登录 + AI 路由（对接数字员工平台 · 客户端侧）

> ⚠️ **2026-06-25 校准（会员重构 + 平台已上线）**：本节部分子节写于会员重构（2026-06-24）前；**客户端接入的逐条契约以同目录《RedBeacon-平台接入开发规范.md》为准**。校准要点：① **算力点已从"挂 entitlement"改为账号级 `membership` 跨员工共享点数池**（一份会员玩遍全平台，§5.2 已改）；② **过渡态废止**——平台后端已上线在产，客户端直接做正式态、不再回退直连 aihub（§5.7 已改）；③ **轻打卡不拉"公告"**（平台未做公告，§5.7 已改）；④ 客户端清单补 **§9 错误码映射 / 临期提醒 / 生图 `request_id` 幂等 / 号数软控值 free1·Pro3·Max5**（详见接入规范）；⑤ 号数/mimic 等分档功能由 **checkin 下发的 `features` 块**驱动（平台已定下发、客户端无脑读不硬编码）。

### 5.1 ⚠️ 安全现状（已查证，务必认清）
- 闭源 CLI 实为**纯 setuptools 打包，wheel/sdist 里 44 个明文 `.py`、零编译**。"闭源"只是法律牌子，技术上=开源：每个用户 site-packages 里躺着全部可读可改源码。
- `services/license.py` 用 Ed25519 签名（密码学无懈可击、无私钥造不出解锁码），**但强制点是可删的明文一行**：用户把 `is_unlocked()` 改 `return True` 或 `max_accounts()` 改 `return 99` 即破，且纯离线从不回服务端复验。
- 私钥/发码脚本没漏进分发包（只混进无害 tests），这点 OK。
- ⚠️ **铁律**：无法对"必须使用密钥的那台机器"隐藏该密钥。对称加密 / 用完即抛都不解决——**客户端能解密 = 抓包者能解密**。客户端只要握有"能直接打中转站/直接读写飞书"的强凭证，就一定会泄。
- 推论：**别用客户端校验守任何值钱的东西。把闸门从"用户的电脑"搬到"你的服务器"。**

### 5.2 ✅ 计费模型：对接平台 freemium + 订阅 + 算力点（弃解锁码、弃钱包/充值）
- **弃**「解锁码买断 + 绑机 + 离线」——与"持续烧成本的可变开销"结构错配、防不住。
- **弃**早期设想的「账户 + 钱包余额 + 按量充值」——可充值/可消费的"算力点货币"触及储值/预付卡合规红线，已在平台层否决（见平台 doc §0.6 / 计费合规 §1）。
- **改为对接数字员工平台的 freemium + 订阅 + 会员配额模型**（平台 = 唯一真源）：
  - **免费归宿主**：定位/选题/文案/内容/文字卡渲染/发布 = 用户自己的宿主 AI（Claude Code / Codex）+ 本地完成，**免费、不经平台**（路 B）。
  - **收费归平台**：RedBeacon 是平台第一个 **metered 员工**，**唯一付费平台能力 = 生图**（按真实成功张数扣**算力点**，N=张数×单价；不生图不消耗）；**仿写**由 `features.mimic` 开关解锁（见 §4.5）。
  - **算力点 = 非货币、不可充值/转让/转售的包月配额**，挂在**账号级会员 `membership` 的跨员工共享点数池**上（2026-06-24 会员重构——原"挂 entitlement"作废；一份会员玩遍全平台所有员工收费能力）、到期作废；要更多额度走**升档**、不做加购（合规）。客户端拉点数走 `checkin.membership.points`。
  - **可发布号数**按档位软控（`max_xhs_accounts` = **free 1 / Pro 3 / Max 5**，已定；**值由 checkin 下发的 `features` 块给**、客户端无脑读不硬编码；客户端本地软控、可破，符合"能破就破"）；**不卖无限号、不打矩阵卖点**（合规最危形态）。
- 登录方式：**平台账号 = 手机号验证码为主**（顺带满足实名基础），微信扫码后续可选、不做用户名密码。CLI 侧用 **device flow** 拿账号级设备令牌（见 §5.7）。
- 机器码降级为**绑设备 / 防滥用指纹**，不再是授权手段；`services/license.py` 的 Ed25519 强制点整体下线（清理项）。

### 5.3 ✅ 核心拓扑：路 B —— 文案走宿主（免费），只有生图带令牌走平台
```
客户端（RedBeacon skill+CLI，跑在用户宿主 AI 里）
  · 文案/选题/定位/内容 = 宿主 AI 自己写，免费、不经平台、不调任何 AI API
  · 只有「生图」带账号级设备令牌调平台
  · 持：设备令牌(绑账号、可吊销)；不持：任何上游/中转站 key
        │ 生图：HTTPS + Bearer 设备令牌（KB 级小包）
        ▼
   数字员工平台 · 生图网关（持上游 key，服务端）
        │ 认令牌 → 查 entitlement 权益 → 原子扣算力点 → 调 new-api 出图 → 落 OSS
        ▼
   new-api（内网，OpenAI 兼容图像渠道，可热切上游 / failover）
```
- 客户端**只持账号级设备令牌**；上游/中转站 key **只活在平台服务端**。抓包客户端最多花用户自己那点算力点，碰不到 key / 别的用户 / 上游。
- **文案不再由 CLI 调 API**：现状 `tasks/generate.py` 直连 aihub 的文案调用下线，改由宿主 AI 在 skill 层写好 JSON 交给 CLI 渲染/入库；出图改为带令牌走平台网关（见 §5.7 落地）。
- 鉴权/扣点一律平台服务端、每次现查、**fail-closed**（DB 不可达即拒、不白烧）。**飞书读写不在此列**（§5.4，CLI 直连）。

### 5.4 ✅ 飞书读写：CLI 直连，不走网关
- 因为采用「每用户自带飞书应用」（§2.3），用户的飞书钥匙**只能访问他自己的飞书**——放用户本地、CLI 直连飞书 API 即可，扒出来也只碰自己数据，**零跨用户风险**。
- 所以**飞书不需要走网关**（网关只管 AI + 出图）。早期担心的"总钥匙发给所有人"问题在此模型下根本不存在，已排除。
- 推论：网关后端不持飞书凭证，飞书 ops 不加网关延迟，后端范围更小。

### 5.5 ✅ 后端归属：平台是外部依赖，本文不展开
- 计费/登录/生图网关的后端（身份 + 权益 + 算力点 + 生图代理 + new-api + OSS/CDN + 支付）= **数字员工平台**，唯一真源 = 《数字员工平台-开发文档.md》(v3)。
- RedBeacon 在该平台上是**第一个 metered 员工**；本方案只写**客户端如何对接**，不重复后端设计。
- ⚠️ **前置依赖（回答"还差什么"）**：客户端的登录/生图改造**依赖平台后端先就位**（平台 doc 的 T0–T5：服务+DB / 手机验证码账号 / device flow 配对 / 权益模型+手动开通 / 生图网关 / new-api 内网 / OSS）。平台未就位前，RedBeacon 走 §5.7 的**过渡态**。

### 5.6 ✅ 出图大负载解法：控制面 / 数据面分离
```
客户端 ──"生成图,prompt X"(小)──▶ 网关 ──(中转站key,服务端)──▶ 中转站出图
                                    │  图落到对象存储(OSS/COS/S3)
                                    ▼
客户端 ◀──短时效预签名下载URL──── 网关
   │
   └──直接从 对象存储/CDN 拉图（重字节走这里，不碰网关）
```
- **控制面**（鉴权/查权益/扣算力点）过网关，KB 级小包；**文案不过网关**（走宿主）。
- **数据面**（图片重字节）走对象存储 + CDN 预签名 URL，弹性按量付费，不占网关带宽。
- ⚠️ 诚实修正：第三方中转站一般不会帮你直传你的对象存储 → **网关多半要中转每张图一次（服务端一跳，仍便宜）**；只有自有中转站能做到直 PUT。客户端下载走 CDN 这条始终成立。
- ✅ 结论：**不必为出图买"大带宽中枢服务器扛全部 AI 字节"**；大带宽中枢是退路不是必需。
- 与现有流程兼容：CLI 本就把图下载到本地 `~/.redbeacon/data/images/` 再用 cloakbrowser 发布——新模型只是把图来源从"中转站直链"换成"平台下载 URL"，客户端拉下来缓存本地、照旧发布。

### 5.7 ✅ 客户端改造清单 + 过渡态（本次 RedBeacon 范围）
**改造清单（仅客户端）**
- **路 B 落地**：`generate` 降级为「渲染 + 入库 + 出图」；文案 JSON 由宿主在 skill 层先写好传入，CLI 不再调文案 API。纯文字卡路径全程零平台、零成本；含 AI 图才带令牌调平台扣点。生图失败/平台不可达只影响图，文字卡笔记照样落库、可后补图。
- **平台登录**：新增 `redbeacon login`（OAuth 2.0 device flow）——弹配对码+短链，用户在浏览器（已登录平台）授权本机 → 拿**账号级设备令牌**存本地隐私内核目录。
  - ⚠️ **命名去冲突**：现有 `redbeacon-login`（扫码登录**小红书**）改名 `redbeacon xhs-login`（或并入 accounts）；`redbeacon login` 专指**平台账号**登录。两个 login 是两套东西（平台登录 ≠ 订阅 ≠ 小红书登录态）。
- **config 重构**：移除用户自填的 `ai_api_key / ai_base_url / ai_model / image_model`（文案走宿主无需 key、生图走令牌、模型由平台服务端别名选）。`redbeacon-config` 从「AI + 飞书 + 代理」改为「**平台登录 + 飞书 + 代理**」。
- **新增 `redbeacon doctor`**：自检/修复运行时（Python/uv、playwright 内核、登录态/令牌、小红书 cookie），对常见故障给可执行修复动作。
- **弃解锁码**：下线 `services/license.py` 强制点。
- ⚠️ **免费也需注册+配对（onboarding 实质变化）**：改后**连免费功能也要先注册平台账号 + device pair**（现状零平台账号即可用）。首启「轻打卡」（`POST /device/checkin`）拉一次**会员状态/权益**（不调 AI、近乎零成本），让平台看得见免费用户。（**公告暂不做**——平台 checkin 无公告字段。）

**过渡态（✅ 已废止——平台后端已上线在产，2026-06-25）**
- ~~生图回退直连 aihub、不计费、不要求平台登录~~ → **作废**：平台生图网关已上线在产（真出图、真扣点验过），客户端**直接做正式态（令牌走网关）**、不必实现过渡代码。
- ▶ 据此**立即摆脱"本地持中转站 key"的安全隐患**（§5.1 痛斥的现状）——正式态客户端零上游 key。

## 6. 自检：已知风险与未解细节（开发须正视）

1. **✅ 已排除（原 🔴）**：飞书 app_secret 跨用户暴露——因采用「每用户自带飞书应用」模型（§2.3/§5.4），用户钥匙只碰自己数据，此问题不存在。
2. **✅ 已澄清（原 🟠 缓存失效）**：本方案**不设计本地缓存**（"图片下载到本地"是发布用素材，非缓存）。无缓存即无缓存漂移问题。
3. **✅ 已接受（原 🟠 离线即死）**：RedBeacon 本就是网络应用——大模型必须联网、飞书联网只是顺带；换来"换设备/不挑地点续上进度"的优势。强依赖网络是设计初衷、可接受。数据膨胀靠热/冷分离 4 表 + skill 层自检（如选题>20 提示清理）+ 归档控量；远期单表行数上限概率极小、推迟解决。
4. **✅ 已解决（原 🟠 富 Base 开通）**：沿用现有"公开模板 + 用户自己 app 调 `/copy` 全自动复制进自己租户 + 转所有者"机制（已跑通、零手动），只需把模板扩成满配 4 表 Base；一次 copy 整体搬走结构。保留复制后 API 校验补齐 + 保真实测。见 §2.4。
5. **🟡 防御性读取**：飞书能被用户手改成代码没造过的状态（手填阶段、删字段），CLI 读飞书须当不可信数据校验。
6. **🟡 跨表一致性**：选题表"已生成/已发布"要与内容审核表真实状态同步，发布时 CLI 须**同时更新两条记录**。
7. **🟡 出图字节**：网关多半中转每张图一次（见 §5.6 修正），非"零字节过网关"。
8. **🟢 网关 HA**：**只有生图走网关**（路 B 后文案走宿主、飞书直连，均不受网关影响）；网关挂＝仅生图停、文案/文字卡笔记照常。影响面比早期"所有 AI 走网关"小，仍需冗余（详见平台 doc）。
9. **🟢 COGS 定价**：额度定价须先算清每次生成/出图的真实成本。
10. **🟢 会话 token 滥用**：额度封顶花费但不封滥用模式（脚本/转售），辅以限流 + 异常检测。

## 11. skill 改造要点（对照现有 skill，适配新表结构）

### 11.1 选题 skill（规划会 redbeacon-topics）
1. **落飞书选题表、不再本地 DB**：`topics batch` 改为写飞书选题表行（含 内容类型/应用域/问题类型）。录入由 AI 做。
2. **出题填核心层、蓝图留空**：量产以核心层为主，蓝图层写时补；蓝图空时继承账号数据。
3. **新增"灵感"态**：拍板落「选题」、没拍板或仿写来的落「灵感」，灵感箱视图待拍板转选题（现有 skill 无此态）。
4. **盘面改从飞书聚合**：摆盘面/by_domain/库存从飞书选题表读（阶段=选题、按应用域分组），不读本地 stats。
5. **继承 + 边界过滤**：关键词/聚焦人群/配图方向默认继承账号数据、不重复问；出题避开账号数据「选题边界·不做」。
6. **去掉 `is_used`**：写成文案=从选题表删除（移文案审核表），库存=阶段为选题的行数，不再标 used。

### 11.2 生成 skill（redbeacon-generate）
1. **取题/拼提示词都从飞书**：从飞书选题表取题；提示词变量从飞书账号数据表拼，不读本地 SQLite 策略。
2. **写成文案的落地**：删该选题行 + 文案审核表 create（快照 标题/文案/标签/图片/内容类型/应用域/选题快照/配图方式，状态=未审核）。
3. **单篇共创写进 brief**：落地想法写进该选题的 角度/提纲 字段再 generate（替代旧 `--idea` 注入 + `topics edit --idea`），想法持久在 brief 上。
4. **配图方式默认读账号数据**「默认配图方式」，单篇保留 `--image-mode` 临时覆盖。
5. **选题低预警**从飞书选题表 阶段=选题 计数。
6. **`ui topics` 网页挑题可退役**：用飞书选题表「写作台视图」替代（用户在飞书勾/排），减少本地 UI（呼应面板退休/瘦壳）。

### 11.3 发布 skill（redbeacon-publish）
- `publish` 回写从"标已发布"改为 **move-to-archive**：成功→归档表 create + 审核表 delete + 回写笔记链接；失败→状态=发布失败 + 失败原因。
- "只发飞书『通过』记录、发布前登录态校验"不变。
