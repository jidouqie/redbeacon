# 持续兼容旧数据的升级流程

每个新版本都执行同一套兼容检查。软件版本与数据库结构版本独立：软件更新但数据格式未变时，不反复转换；用户跳过多个版本时，按保留的完整历史链转换。

## 固定流程

1. 检查数据库版本记录、SQLite 完整性和数据关联；核对实际表、字段类型、主键、必填约束、默认值、唯一性和关联约束。版本号相同也要核对实际结构。
2. 结构兼容时直接使用。历史扩展字段和表可以保留，不为追求格式完全相同而删除。
3. 需要转换时取得 SQLite 写锁，阻止其他进程在备份与提交之间改写数据。通过 SQLite backup API 生成包含已提交 WAL 的一致快照，写入校验和并持久化；备份失败立即停止。
4. 在隔离副本上顺序执行缺失的历代迁移。每一步核对原有行、字段值和重复行数量，转换后再验完整性与目标结构。
5. 副本通过后，在原库的同一个 SQLite 事务中执行转换并再次校验，最后提交。原数据库文件不换名替换，避免其他已打开连接继续写旧文件。
6. 出错时回滚并停止启动，保留备份和具体原因。不会建空库冒充成功，也不会自动用旧快照覆盖用户之后的新工作。

升级前快照位于当前数据库旁的 `migration-backups/`，每次目录独立，含 `before.sqlite3` 和 `backup.json`。它是完整 SQLite 备份；图片、浏览器登录目录与平台令牌等外部文件由本流程原地保留，不属于该 SQLite 快照的内容。迁移备份不自动滚动清理。

## 后续版本的维护规则

- 保留从第一版开始的连续迁移清单，只追加新步骤。不能删除“上次已经迁移过”的旧步骤，也不能修改旧步骤来代替新增迁移。
- 迁移仅操作当前连接中的数据库，不进行联网、发布、图片改写、独立文件变更或显式事务提交。副本演练和目标格式推导会执行这些规则，不能包含外部副作用。
- 默认采用增加字段或表的转换方式，保留旧值。需从旧格式派生新字段时，写入新字段并验证，保留原字段用于追溯。
- 历史基线中已存在的代理加密、旧配置搬移等转换使用限定的逻辑等价比较；账号、选题、正文、图片路径、审核状态、生成来源和排期没有宽松跳过规则，完整原始数据库仍保存在快照中。
- 已发布旧库的两项创作回退策略可能仍声明默认值 `ask`；现有业务明确将其解释为 `allow`，且保存时显式写入策略。兼容检查保留这一已知等价表示，不能因此拒绝正常旧库，也不扩大为任意默认值放行。
- 增加迁移时，同时验证早期版本直升和最近版本升级。数据库标记与实际结构冲突、结构来自更新的客户端、数据损坏或没有对应转换规则时，保留原件并停止，禁止猜测修复。

## 与现有安装流程的关系

现有安装器在替换应用前，用新包对旧数据库快照执行桌面初始化验收；该初始化复用上述流程。安装健康检查仍使用隔离数据库。安装器和对外安装命令没有改动。

真正的用户数据库在新客户端首次启动时，再经过同一套检查和事务转换。开发客户端和 CLI 也不能绕过。若这一步因磁盘或数据问题失败，业务数据保持事务开始前的状态；这不等于承诺已安装的新应用也自动降回旧版本。

数据升级后，较老客户端仍可能无法理解新增格式；应使用支持该格式的客户端，不能仅把数据库版本号调低。保护原数据和保留历史迁移链，保证的是旧数据向新版本安全升级。

本次修复未增加数据库结构版本，当前仍为 3，也未发布新版本。

- 对本机正式与测试业务库只进行只读完整性和结构检查；没有在真实业务库中试验转换，也没有提交笔记。
