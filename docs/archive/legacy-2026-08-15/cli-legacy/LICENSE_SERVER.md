# RedBeacon 发码系统搭建要点

多账号解锁的授权方案与服务端搭建说明。配套代码：
- 客户端验签：`src/redbeacon/services/license.py`
- 机器码定义：`src/redbeacon/utils/machine.py`
- 发码签名工具：`tools/sign_license.py`

---

## 一、原理：Ed25519 非对称签名

```
你（服务端，持私钥 🔒）          用户（CLI，内置公钥 🔓）
─────────────────────          ──────────────────────────
解锁码 = sign(机器码, 私钥)      verify(解锁码, 本机机器码, 公钥) → 通过才解锁
```

- **造不出注册机**：没有私钥就签不出有效码。客户端被逆向也只能拿到公钥（公开无害）。
- **绑机器**：签名对象是机器码，换台机器机器码变了，验签必败 → 码无法转卖/共享。
- **离线验证**：用户激活时 CLI 不联网，纯本地数学验签。
- **服务端极简**：核心只有「收机器码 → 验付款 → 私钥签名 → 返回解锁码」。

### 解锁码格式
对机器码做 Ed25519 签名得 64 字节，再 `base32`（无填充、大写）编码，约 103 字符。
用户输入时大小写 / 空格 / 连字符都会被 CLI 规范化（`license._normalize`），容错友好。

### 机器码（用户侧 `redbeacon license info` 产出）
`sha256("{system}|{node}|{MAC}")` 取前 16 位十六进制大写。服务端**无需复现**此算法，
直接对用户提交的机器码字符串签名即可。

## 二、上线前必做：换正式密钥

当前仓库内置的是**开发用公钥**，开发私钥在 `tools/dev_private_key.hex`（已 gitignore）。
**正式上线前务必换一对全新密钥**，私钥只留服务器，绝不进客户端仓库。

```bash
# 在服务器上生成新密钥对
python tools/sign_license.py --genkey
# 输出：
#   PRIV_HEX(保密，只留服务器): <私钥hex>   ← 存进服务器密钥管理，绝不外泄
#   PUB_HEX (填入 license.py): <公钥hex>    ← 替换 license.py 的 _PUBLIC_KEY_HEX
```

把 `PUB_HEX` 填进 `src/redbeacon/services/license.py` 的 `_PUBLIC_KEY_HEX`，重新打包客户端。
私钥通过环境变量 `REDBEACON_PRIV_HEX` 注入服务端，不落地到磁盘。

## 三、签发一个解锁码（手动 / 服务化）

### 手动（早期，量小时完全够用）
收款后，拿到用户的机器码，跑：

```bash
REDBEACON_PRIV_HEX=<正式私钥hex> python tools/sign_license.py <用户机器码>
# 输出解锁码，发给用户
```

用户运行 `redbeacon license activate <解锁码>` 即解锁。**早期可以纯人工，不必搭服务。**

### 服务化（量大时）
一个最小 HTTP 接口即可：

```
POST /issue
  body: { "machine_code": "...", "order_id": "..." }
  1. 校验 order_id 已支付（对接你的支付回调 / 订单库）
  2. 防重放：同一 order_id 只签一次，记录 machine_code ↔ order 绑定
  3. code = base32(ed25519_sign(machine_code, 私钥)).rstrip("=")
  4. return { "license_code": code }
```

签名逻辑直接抄 `tools/sign_license.py` 的 `_sign()`。私钥从环境变量读，进程内存持有，不写盘。

## 四、购买页交互（建议文案）

1. 让用户先运行 `redbeacon license info`，复制其中的 **机器码**。
2. 购买页填机器码 + 下单付款（¥199 一次性买断多账号）。
3. 付款成功后展示 / 邮件发送 **解锁码**。
4. 用户运行 `redbeacon license activate <解锁码>` 完成解锁。

## 五、可选增强（按需，非必需）

- **档位 / 过期**：把签名 payload 从纯机器码改成 `机器码|过期时间戳|档位`，客户端验签后解析，
  支持订阅制或多档位（如 pro / team）。当前买断制只签机器码即可。
- **吊销**：买断 + 离线验证天然无法远程吊销。若需要，得引入联网校验或短期 token，
  会牺牲离线优势，一般不值得。
- **机器码稳定性**：当前机器码含 MAC（`uuid.getnode()`）。换网卡 / 部分虚拟机环境下 MAC 可能变，
  导致需要重新发码。若要更稳，可改用主板 / 磁盘序列号等，但跨平台获取更复杂，权衡取舍。

## 六、威胁模型小结

| 攻击 | 是否防住 | 说明 |
|---|---|---|
| 逆向客户端做注册机 | ✅ | 只拿到公钥，签不出有效码 |
| 一码多机共享 | ✅ | 码绑机器码，换机即失效 |
| 改 DB 里的 `license_key` | ✅ | 每次启动都重新验签，无效码不放行 |
| 改客户端代码绕过验签 | ⚠️ | 本地软件的固有上限。建议二进制打包（pyinstaller）抬高门槛 |
| 私钥泄露 | ❌ | 一旦泄露全盘皆输。私钥只走环境变量、只留服务器、严格管控 |
